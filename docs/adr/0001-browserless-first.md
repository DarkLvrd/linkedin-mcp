# ADR-0001: Browserless-first with a three-way transport routing

LinkedIn's web app talks to two private APIs — Voyager (reads, plus browserless writes) and SDUI (profile edits, comments, deletes) — and research verified that most writes work over plain HTTP with fresh session cookies (mguttmann/linkedin-internal-api, captured from live traffic). The bridge we replaced drove every write through a browser, which triggered LinkedIn's fingerprinting and the authwall after ~2–3 browser writes per sign-in. We decided the server is **browserless-first**: all reads and most writes go over HTTP (Voyager + SDUI), and a stealth browser is used only as the session source (login, cookie persistence) and as a per-capability fallback for the SDUI writes that 500 without a page context. The v1 routing table: **Voyager** — all reads, post-create/edit, like, save/unsave, delete-repost, all messaging, connect-with-note, follow-company, media upload; **SDUI** — all profile edits (skills add/delete, top-skills via the About form, experience, education, …), comments, unlike, delete-post, endorse, remove-connection; **browser fallback** — behind a per-capability flag. Rejected: browser-first (the bridge model) — slower, and each browser write spends the per-sign-in budget that ends in the authwall.
